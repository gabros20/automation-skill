# Approval Policy Card

Fill this out **before** the gate goes live — not the first time a request times out. A timeout
default chosen after requests are already pending is not a policy, it is whatever happened to be
convenient at 2am. Source: [`references/approval-and-authority.md`](../references/approval-and-authority.md).

**How to fill a new card:** name the action being gated first, then work down. "Who may approve" is
usually obvious; the timeout default is the row worth the most thought, because every engine leaves it
blank by default (I13). Where the approver would otherwise be the same identity that proposed the
action, don't write "the owner" twice — resolve it against the n=1 case in
`references/approval-and-authority.md` (§4) before filling the row.

## Worked example

| Field | Filled |
|---|---|
| Action gated | Refund over $500, generated by the refund-request automation from a matched support ticket |
| Who may approve | Owner — reviewing a system-proposed action, not their own manual entry: the maker is the rule, the checker is the person |
| Requester = approver? | No — the maker is the automation, not the owner. Re-check this stays true if the owner can silently edit the matching rule; an "independent" check is only as independent as the rule it depends on (I6) |
| Timeout duration | 4 business hours |
| Timeout default (deny / allow / escalate) | Deny (fail closed) — an unreviewed refund does not go out; the customer waits, the money doesn't move |
| Escalation path | None above the owner at n=1 — the timeout default *is* the escalation |
| Evidence logged | The original support ticket, the matched decision-table row, the amount, and the owner's decision — logged as a fact independent of the refund actually being issued |
| n=1 compensating control | Independent reconciliation: the refund is checked against Stripe's own record within 24 hours, not against this workflow's own log of having sent it |

Fail-closed is the right default for anything irreversible; if this card sets the default to allow,
write down why the cost of a false block outweighs the cost of an unreviewed action going through —
that reasoning is the part most likely to be second-guessed later.

**Self-audit:** if "who may approve" and "requester" would resolve to the same identity acting in two
roles, this card is not done — go back to `references/approval-and-authority.md` (§4) before shipping
it as approved.
